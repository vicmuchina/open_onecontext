OpenContext Agent Guide
=======================

Why This Exists
- This guide is the source of truth for coding agents working in this repo.
- It explains how to keep long-running OpenCode sessions aligned with GCC memory discipline.
- It is generated by OpenContext so agents can bootstrap quickly without rereading the whole codebase.

System Purpose
- OpenContext provides project memory in .GCC (commit history + logs + metadata).
- The Law Enforcer plugin continuously inspects workflow behavior and enforces rules.
- Enforcement can be deterministic (JSON rules) and model-judged (watchman over policy text).

Core Files
- .GCC/main.md: project goal and milestones.
- .GCC/branches/*/(commit.md, log.md, metadata.yaml): branch memory artifacts.
- /home/vic/Projects/RLM/.GCC/law-enforcer.json: machine-readable law config (JSON).
- /home/vic/Projects/RLM/.GCC/law-policy.txt: plain-text workflow law document for watchman judgment (ships with active balanced defaults).
- /home/vic/Projects/RLM/.GCC/law-watchman-system.txt: editable watchman system prompt (controls judgment style/strictness).
- /home/vic/Projects/RLM/.GCC/law-failure-policy.txt: editable failure-lookup classifier policy (actionable vs noise).
- /home/vic/Projects/RLM/.GCC/law-research-policy.txt: editable research-capture classifier policy (what must be checkpointed).
- /home/vic/Projects/RLM/.GCC/law-runtime.json: optional project-local provider secret/model overrides.
- /home/vic/.config/opencontext/law-runtime.json: optional global provider secret/model overrides.
- .GCC/law-enforcer-trace.jsonl: runtime evidence log for requests/responses/violations.

Runtime Components
- Plugin: opencontext-reminder.js (global ~/.config/opencode/plugins or project .opencode/plugins).
- CLI: opencontext (must be installed and available in PATH).
- Provider key: env var referenced by `critic.apiKeyEnv`.
- Provider type: OpenAI-compatible chat completions endpoint.

Enforcement Lifecycle
- session.created: initialize state, show GCC/MCP awareness.
- experimental.chat.system.transform: inject law contract + policy/hints.
- tool.execute.after: update debt, evaluate deterministic + custom rules.
- message.updated (assistant completion): run watchman inspection.
- session.idle: safety pass.
- session.compacted: record compaction event; deterministic mode can open debt immediately, model mode judges recovery need.

What Watchman Sees
- Current law config summary.
- Plain-text policy (/home/vic/Projects/RLM/.GCC/law-policy.txt).
- Recent assistant/user messages.
- Recent tool calls (tool name + command + output snippet).
- Recent interruptions + post-alert actions (to avoid repeating already-satisfied alerts).
- Recent debt transitions (open/clear history).
- Debt state (checkpoint/research/failure/mcp).
- Per-rule custom violation counters.

What Watchman Must Return (strict structured JSON)
- violation: boolean
- rule: string
- reason: string
- correction_prompt: string
- confidence: number
- optional satisfaction_evidence: string
- optional debt_updates: pendingCheckpointOverdue|pendingCompactionCheckpoint => open|clear|keep
- optional assist:
  - should_suggest: boolean
  - confidence: number
  - reason: string
  - suggestions[]: title, why_now, action, optional command, memory_refs[]

Malformed Output Handling
- The plugin requests structured JSON output (default `json_schema`, optional `json_object` fallback).
- If malformed, it retries with stricter instruction (`strictJsonRetryAttempts`) and can fall back by `critic.responseFormatStrategy`.
- If still malformed, it logs and skips interruption (no broken prompt injection).

1) Provider + model config (in /home/vic/Projects/RLM/.GCC/law-enforcer.json, section `critic`)
   - baseUrl, endpointPath, authHeader, apiKeyPrefix, headers, request, model, modelFallbacks, apiKeyEnv, modelEnv, responseFormatStrategy.

5) Natural-language policy updates (/home/vic/Projects/RLM/.GCC/law-policy.txt)

6) Watchman system prompt updates (/home/vic/Projects/RLM/.GCC/law-watchman-system.txt)

8) Research capture policy updates (/home/vic/Projects/RLM/.GCC/law-research-policy.txt)

Purpose
- Benchmark OpenAI-compatible models for strict JSON output reliability + speed
- Originally built for Chutes, works with any OpenAI-compatible provider
- Auto-selects best model + fallbacks and writes to runtime config

Usage

Basic Benchmark (auto-discover models from /v1/models endpoint)
```bash
export PROVIDER_API_KEY="your_api_key"
python3 scripts/chutes_json_benchmark.py \
  --base-url https://<provider>/v1 \
  --api-key-env PROVIDER_API_KEY \
  --response-format json_object \
  --top 10
```

All Available Flags

Provider Configuration:
  --base-url BASE_URL           Provider base URL (default: https://llm.chutes.ai/v1)
  --models-url MODELS_URL       Override model-list endpoint URL
  --chat-url CHAT_URL           Override chat-completions endpoint URL
  --provider-name NAME          Label only (report metadata)

Authentication:
  --api-key-env ENV_VAR         Env var name for API key (default: CHUTES_API_KEY)
  --api-key KEY                 Explicit API key (overrides env)
  --auth-header HEADER          Auth header name (default: Authorization)
  --api-key-prefix PREFIX       Auth prefix (default: Bearer, empty for raw key)
  --extra-header KEY=VALUE      Additional header (repeatable)

Model Selection:
  --models LIST                 Comma-separated model IDs (bypasses /v1/models)
  --max-models N                Limit number of models (0 = all)
  --include-regex REGEX         Only test model ids matching regex
  --exclude-regex REGEX         Skip model ids matching regex

Benchmark Configuration:
  --response-format FORMAT      json_object or json_schema (default: json_object)
  --max-tokens N                Max completion tokens per case (default: 140)
  --timeout SECONDS             HTTP timeout seconds (default: 45.0)
  --delay-ms N                  Delay between requests (default: 0)

Output:
  --top N                       Rows to print in leaderboard (default: 20)
  --output PATH                 Output JSON file path
  --list-only                   List models and exit (no benchmark)

Runtime Config:
  --write-runtime PATH          Write best model + fallbacks (repeatable)
  --fallback-count N            How many fallback models to write (default: 3)
  --include-api-key             Also persist API key into runtime file

TROUBLESHOOTING PROVIDER ISSUES
================================================================================

Problem: HTTP 404 on /v1/models
Cause: Provider doesn't expose model list endpoint (e.g., DashScope)
Solution: Use --models flag with hardcoded model list

Problem: HTTP 401 Unauthorized
Cause: Invalid or missing API key
Solution: 
- Verify env var: echo $DASHSCOPE_API_KEY
- Check runtime config: cat .GCC/law-runtime.json
- Ensure apiKeyEnv matches actual env var name

Problem: HTTP 404 on /v1/chat/completions
Cause: Wrong endpoint path
Solution:
- Try --chat-url override
- Check provider docs for correct endpoint
- Some providers use /chat/completions, others use /completions

Problem: Model returns non-JSON output
Cause: Model doesn't support response_format parameter
Solution:
- Use --response-format json_object (more widely supported)
- Try different model (some models don't support structured output)
- Check provider documentation for JSON mode support

Problem: High latency (>10s)
Cause: Slow model or network issues
Solution:
- Run benchmark to find faster models
- Increase critic.timeoutMs in law-enforcer.json
- Consider switching to faster provider (e.g., Groq for Llama models)

Problem: Schema compliance <100%
Cause: Model struggles with strict JSON schema
Solution:
- Use simpler models designed for code generation
- Try --response-format json_object instead of json_schema
- Exclude problematic models from fallbacks

================================================================================
SECURITY NOTES
================================================================================

API Key Security:
- Never commit API keys to git (ensure .GCC/law-runtime.json is in .gitignore if it contains keys)
- Prefer environment variables over file-based keys in production
- Rotate keys periodically via DashScope console
- Use project-local runtime config for team sharing (with key redacted)

Runtime Config Precedence:
1. Environment variables (highest priority)
2. Project runtime config (.GCC/law-runtime.json)
3. Global runtime config (~/.config/opencontext/law-runtime.json)
4. law-enforcer.json defaults (lowest priority)

This means you can:
- Store non-sensitive config in runtime files
- Keep API keys in environment variables
- Override models per-project without changing law-enforcer.json
